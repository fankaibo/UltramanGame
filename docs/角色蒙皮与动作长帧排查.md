# 角色蒙皮与动作长帧排查

A-20261011-118，基线 `a77f241`。目的为处理会打断战斗动作的长帧，不代表提前完成 60 FPS 或内存专项。

## 实际证据

上一轮严格体感回放曾在 1182.8 ms 长帧后失去新鲜姿态，暂停并取消已发射光弹。新版真实相机运行约 12 分钟后也出现 processed frames stopped；恢复期间一次摄像头未返回画面，后续工作代恢复再停止。没有调整识别或新鲜度阈值以绕过这些问题。

2026-10-11 对实际 A-117 游戏和相机各做 3 秒只读 native sample，保存在 `artifacts/runtime-stall-20261011/`，没有录制相机画面：

- 游戏 physical footprint 约 1.4 GiB，进程生命周期峰值 2.2 GiB；RSS 当时约 204 MiB。这两个口径不能混用。
- 相机 physical footprint 约 330 MiB；采样中主线程多数时间等待 MediaPipe 推理任务，未由这份短采样证明死锁。
- 游戏渲染工作线程 221 个样本中，42 个处于几何任务栅栏路径；多个工作线程出现 CPU 顶点蒙皮函数。项目 `meshDeformation=0`、`gpuSkinning=0`。
- 系统交换空间占用约 13.3 GiB，还有其他应用运行。采样能确定 CPU 蒙皮在渲染依赖链上，但不能据此断言它是全部长帧或相机断流的原因。

## 候选与对照方法

候选仅由 `ProjectSetup.Configure` 指定 `PlayerSettings.meshDeformation=MeshDeformation.GPUBatched`，不减模型顶点、贴图、分辨率或特效。[Unity 6000.6 官方 API](https://docs.unity.com/en-us/engine/6000.6/script-reference/unityeditor/playersettings/meshdeformation)说明，该模式将角色蒙皮放到 GPU 批处理；此处效果仍以本项目实际包为准。

首次候选构建未连接上 Unity Package Manager 本地 IPC，退出 1，保留 `logs/a118-build-upm-failed.log`。关闭旧试玩后原构建重跑成功，签名通过，候选没有覆盖默认 A-117。

顺序运行原版 CPU 与候选 GPU 的同一 `cinematic_player_check.py --claw-cycle --timeout 600`，要求五种怪兽攻击、两次必杀、受击／防御和胜利都通过，并保留真实角色和阴影截图；本轮撤回前未完成候选截图的人工视觉验收。不得把编辑器 BakeMesh 截图当作 GPU 蒙皮视觉验证。全程原版和候选单实例运行，其他用户应用不关闭。

## 结果与决定

两份实际包均完成五攻击整局：32 次普攻、2 次必杀、4 次格挡、1 次受击、暂停恢复和胜利通过。详细报告和路径见 `artifacts/runtime-stall-20261011/skinning-comparison.json`。

| 指标 | 原版 CPU | 候选 GPU |
| --- | ---: | ---: |
| 前两个 10 秒渲染窗口 FPS | 46.8 / 46.9 | 18.1 / 21.2 |
| 全流程墙钟时间 | 194.03 秒 | 156.06 秒 |
| 游戏内验证时间 | 102.04 秒 | 102.46 秒 |

这些指标方向并不一致，且 FPS 窗口只覆盖开始阶段，不能作为整局性能结论。共享机器存在负载变化、截图编码和初次 GPU 管线准备，因此既不能证明 GPU 蒙皮普遍更差，也没有足够证据证明它能稳定解决卡顿。**本轮撤回 GPU 设置，不交付未经证实的性能变更。** 源码和项目设置恢复原值，默认包保持 A-117；候选入口也恢复为同一 A-117，160 个文件哈希一致（`restored-candidate.json`），随后重新打开游戏。

后续先解决采样覆盖范围：需要整局按战斗阶段记录渲染时间、排除截图编码窗口，并做 CPU→GPU→CPU 的单实例交叉对照，再决定是否启用。相机 `GamePreview.publish` 仍在推理主循环同步缩放、画骨架和编码 JPEG；这是潜在阻塞路径，但当前 native sample 主要显示推理等待，尚未证明 JPEG 是上述相机断流的原因，不能据此直接声称已定位或修复。

结论：排除了“仅凭 CPU 蒙皮栈就打开 GPU 设置”的交付方案，保留完整失败与对照证据；长帧和真实相机恢复问题仍未解决，整体街机目标仍未完成，总进度不变。
