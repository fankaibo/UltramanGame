# 姿态消费时钟（A-20261012-121）

源码基线 `0ad766b`。本轮修复主线程工作较久时，新姿态被旧时间误判为未来数据的逻辑缺陷。它可能打断持续大招或举手开始，但不能据此认定此前所有追踪暂停、摄像头断流都由同一原因造成。

## 原因与修复

原顺序是：Update 开始记录 `now` → 预览 JPEG 解码等工作 → 从后台最新帧槽取姿态 → 用最初的 `now` 检查新鲜度。若中间被调度挂起或解码较慢，后台刚收到的姿态会比旧 `now` 新 50 毫秒以上，因而被拒绝，持续姿势进度被清空。

`PoseClient.TakeLatestPose` 现在把解析后的姿态与**解析完成时的本机时间**一起返回。ArenaController 的新鲜度、在场状态和待战姿态观察使用这个时间；空槽或解析失败也刷新消费时间。采集时间仍由摄像头产生，后台线程不调用 Unity JSON API，不排队重播旧帧。

保持原有 350 毫秒过期限制、50 毫秒未来容差、600 毫秒在场宽限及动作门槛。真正过期的数据仍会暂停识别。英雄只通过方向键或点击选择。本轮没有修改预览／合照流各自的时间检查，也没有减少效果或模型。

## 确定性回归

`tests/CoreChecks/PoseReadClockChecks.cs` 使用实际本机 TCP 和生产 `PoseClient` 后台接收器，只对消费时间注入可控时钟：

- 帧开始时刻 100000，模拟预览处理到 100160；收到采集于 100150 的姿态，解析再耗 80 毫秒。旧时钟判为未来数据，100240 的正确消费时间判为有效，原始采集时间不变。
- 解析期间真正过期、真正来自未来、空槽和断流超过宽限均被拒绝；新帧可以恢复。
- 同一组 60 帧“放手 → L 形持续大招”经过真实接收器，旧时钟路径不能释放，修复路径只释放一次。没有靠放宽动作或时间门槛通过。
