# 迪迦体感游戏：首版方案

更新日期：2026-09-08。状态：需求已确认，M0 已运行并加入首轮动作与视听完善。以下保留首版体验目标；当前实现与验证边界分别见 [实现说明](实现说明.md) 和 [验证记录](验证记录.md)，未标记完成的体验不能视为已经实现。

## 1. 已经确认的需求

为 4 岁孩子制作家庭体感游戏。孩子站在摄像头前，通过身体动作参与战斗；变身后，电视画面中的主角是完整的迪迦奥特曼。参考《奥特曼系列：变身大决战》的变身、体感攻击、光线必杀和庆祝体验。

| 项目 | 已确认内容 |
| --- | --- |
| 玩家 | 用户的儿子，4 岁 |
| 第一位英雄 | 迪迦奥特曼 |
| 战斗中的外观 | 奥特曼的样子 |
| 摄像头 | 本机自带前置摄像头；替代此前讨论的智能摄像头 |
| 运行设备 | 本机 MacBook Air，Apple M3，16 GB 内存；配置已通过系统查询核对 |
| 显示设备 | 小米电视 |
| 敌方行为 | 轻度反击，攻击前有明确蓄力提示 |
| 玩家防御 | 孩子可以通过动作防御 |
| 受击与输赢 | 受击后可以恢复，首版不设失败 |
| 首版语音与 AI 范围 | 先完成动作识别和战斗，配固定语音引导；自由语音对话放到后续 |

采用 Unity 6，已使用用户安装的 6000.6.0f1 导入、编译并构建。M0 通过本机 TCP 接入独立 Python 姿态进程。下文的动作、时长、视角和技术细节属于建议默认值，可根据试玩调整。

## 2. 首版建议范围

一个玩家、一个迪迦角色、一个怪兽、一处战场。先支持上半身动作；角色脚部在战斗区域内由动画系统控制。每局以两三分钟为体验设计目标，不用倒计时判负，实际时长通过试玩调整。

电视建议作为 Mac 的外接显示器，优先用 USB-C 转 HDMI 线，或转接器加 HDMI 线建立测试基准。有线连接仍是建议，用户尚未确认已有线材。电脑保持开盖，放在电视附近，摄像头朝向孩子。取景需要覆盖头部、肩膀、手肘和双手的活动范围。

## 3. 一局游戏的流程

| 阶段 | 画面与操作 | 进入下一阶段的条件 |
| --- | --- | --- |
| 准备 | 家长启动游戏；检查摄像头和声音；显示站位提示 | 摄像头可用，家长开始 |
| 入场校准 | 短暂显示镜像真人预览，引导孩子站稳、抬手 | 关键部位持续可见，完成简单校准 |
| 变身 | 提示举手，播放变身演出，正面展示迪迦 | 演出结束；首次试玩可由家长触发 |
| 动作练习 | 分别示范挥拳、防御、光线姿势；成功后给反馈 | 三项体验完成，或家长跳过 |
| 战斗 | 迪迦与怪兽交战；建议从主角身后稍偏侧看向敌人 | 怪兽生命降到零 |
| 庆祝 | 怪兽退场，迪迦庆祝，播放鼓励语音 | 选择再玩或结束 |
| 暂停 | 孩子离开、关键点识别不可靠，或家长暂停 | 重新找回玩家，提示后恢复 |

庆祝合影可以后续加入。根据后续确认，右下角持续提供可收起的真人取景小窗口，便于家长查看识别情况；战斗主体采用迪迦形象。

## 4. 战斗规则

### 身体跟随与招式

2026-09-08 用户确认改用动画式画面、优先角色像原作：当前摄像头动作触发对应战斗插画和移动特效，不再逐关节跟随。识别和战斗逻辑保留，角色展示可预览全部 8 个姿势。

| 输入 | 建议判定方式 | 游戏反馈 |
| --- | --- | --- |
| 挥拳 | 看手腕相对肩膀连续向前或侧前移动；支持左右手，不要求标准肘角 | 播放一次攻击动画，在动画命中时刻扣除怪兽生命并增加能量 |
| 防御 | 双手位于胸前防御区域，并短暂稳定保持 | 显示护盾；敌方攻击结算时仍在防御则挡住攻击 |
| 光线 | 宽松 L 形，或双手约肩宽向前推，保持一小会儿 | 能量充足时播放光线动画，命中后造成较高伤害 |

输入按人体肩宽比例判定，不依赖固定像素距离；目前没有完成个性化校准。2026-09-08 根据“前推不触发、上下移动反而触发”的反馈，使用本机模型输出的估计深度和连续动作判断，支持直接向摄像头前推，同时保留侧前挥拳。单摄像头的实际深度质量、遮挡和儿童手感仍需现场验证。

保持同一姿势只触发一次招式，需要放松或收手后重新准备。设置最短招式间隔，避免识别抖动造成连发。光线与防御输入可能相似，要结合持续时间、能量状态和当前游戏状态消歧；一次输入只接受一种招式。

### 怪兽反击

怪兽依次进入等待、蓄力提示、攻击、恢复。蓄力阶段同时给出明显的视觉提示和简短声音提示；首次默认给孩子较长反应时间，试玩后再调。

- 玩家在攻击结算时防御成功：挡住伤害，给予成功反馈，不增加大招能量。
- 玩家没有防御：播放轻微受击效果；短暂恢复后继续操作，并获得一段保护时间。
- 首版建议不设玩家死亡状态；怪兽攻击用于练习防御与制造节奏。
- 玩家追踪丢失、暂停或胜利后，停止敌方攻击结算。恢复时清除过期输入并给出倒数提示。

### 能量、光线和胜利

每命中 15 次普通攻击攒满一次大招，防御不增加能量。怪兽默认承受 50 次普攻，家长可在游戏设置调整到 10–200 次；光线伤害仍相当于 9 次普攻。能量满后，给出清晰的光线姿势示范；释放成功才消耗能量。识别失败不消耗能量。

普通攻击与光线都能击败怪兽，不强制孩子完成特定姿势才能通关。光线用于提供更明显的高潮。血量、能量和招式时长在动作识别跑通后再调，不把本草案中的体验时长当作已达到的结果。

## 5. 推荐技术分工

核心链路：

摄像头 → 本地人体姿态识别 → 带时间戳的关键点 → Unity 动作判定与角色控制 → 战斗、动画、声音 → 电视。

| 模块 | 建议实现 | 职责 |
| --- | --- | --- |
| 摄像头与识别原型 | Python + MediaPipe Pose Landmarker，采集方式在本机验证 | 提取人体关键点，记录帧时间与质量指标 |
| 本机通信 | M0 使用仅绑定 127.0.0.1 的 TCP JSON 行 | 传送带序号、时间戳、可见性信息的姿态；当前不传送画面 |
| 输入判定 | Unity C# | 校准、平滑、招式识别、冷却和重新准备逻辑 |
| 角色与场景 | Unity | 动作插画、动画衔接、迪迦与怪兽、立体战场和特效 |
| 战斗逻辑 | Unity C# 状态机 | 敌方蓄力、防御、命中、能量、恢复和胜利 |
| 语音 | 固定引导台词 | 示范、攻击预警与鼓励 |

原型阶段让识别进程独占摄像头，Unity 使用该进程提供的姿态。右下角已加入镜像真人预览和关节点，家长可以随时收起。后续是否把识别整体集成到 Unity，在原型稳定、明确打包需求后再决定。

姿态数据只保留最新有效结果，不排队回放旧动作。通信中断或数据超时，与玩家丢失同样处理。界面调试信息由家长入口查看，儿童界面使用图形示范和简短提示。

姿态识别模型负责身体位置。用户已确认首版完成动作识别、固定语音引导与完整战斗。后续如增加通用大模型，可用于对话或剧情；实时战斗继续独立运行。

建议固定台词覆盖以下时机：入场时提示站位，变身时提示举手，练习时示范招式，怪兽蓄力时提醒防御，能量充足时提示光线，受击恢复时鼓励继续，胜利时庆祝。防御预警优先于一般鼓励，同类提示合并，避免声音连续叠加。相机输入足以支撑首版玩法，不需要麦克风输入。

建议默认在本机处理摄像头画面，使用内存缓冲，不自动录制视频或保存照片；如增加纪念合影，再设计明确的保存操作。

## 6. 开发顺序与验收

| 阶段 | 交付内容 | 验收方式 |
| --- | --- | --- |
| 1. 环境与取景 | 核对 Unity/识别运行环境；前置摄像头显示真人和关键点 | 孩子站在实际位置，抬手和挥拳时关键点可见；记录遮挡问题 |
| 2. 动作与角色原型 | 使用临时人形验证手臂跟随、挥拳、防御和光线事件 | 每个动作重复 10 次，记录识别、漏检和误触发；保持姿势不重复触发 |
| 3. 完整战斗 | 一个怪兽、攻击预警、防御、恢复、能量和胜利 | 成功防御、未防御、连续受击、暂停恢复均可继续游戏；不存在失败状态 |
| 4. 迪迦呈现 | 落实可用于项目的角色模型、动画和声音资源，完成变身与战斗演出 | 角色外观符合预期，动作过渡连贯，特效与命中同步 |
| 5. 电视试玩 | 接入小米电视，调整取景、输出和整体延迟 | 在实际摆放条件下完成一局；记录动作到电视反馈的延迟和孩子体验 |
| 6. 家庭使用 | 启动入口、家长暂停/重试、音量与画质设置 | 关闭后可以重新启动；相机不可用时有明确提示 |

识别与输入阶段应记录有意义的结果，尤其是左右手、站位变化、手臂遮挡、身体短暂出画、姿势长时间保持、通信超时和技能结束后恢复跟随。先用这些结果决定是否进入下一阶段。

已加入城市背景、关节角色、动作图示、循环配乐和战斗音效；仍未取得正式迪迦精细模型与动画资源，也未完成真人动作识别准确率或端到端延迟验收。Unity 工程、固定依赖和 macOS 构建已经通过验证；摄像头进行了短时采集与推理测试，整局战斗通过合成动作验证，详见《验证记录》。

## 7. 剩余实现工作

核心产品选择已经收敛。以下工作在实施过程中落实，不需要继续逐项询问玩法偏好：

1. 验证本机 Unity 与识别运行环境、模型下载和相机权限，确定具体依赖版本。
2. 验证 HDMI 线材和电视实际摆放条件；先在电脑上开发，不阻塞前面的原型。
3. 落实迪迦模型、怪兽和动画资源；临时人形只用于早期动作验证。
4. 用孩子实际动作调整阈值、攻击节奏、能量、镜像映射和音量。
