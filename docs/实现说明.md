# M0 实现说明

## 数据链路

Python 独占前置摄像头，MediaPipe Lite 在本机提取姿态。Unity 通过 `127.0.0.1:8765` 获取 UTF-8 JSON 行。初稿中的 WebSocket 调整为 TCP JSON 行，双方均使用标准库即可建立连接，减少原型依赖。

本机固定使用 MediaPipe 1.0.1。Apple M3 上实测默认 CPU 路径在初始化时崩溃；显式 Metal GPU 加 SRGBA 四通道输入通过真实模型测试。`vision/model.py` 统一相机与测试的模型配置，macOS 使用这条已验证路径。其他平台暂用 CPU/RGB，尚未进行原生推理实测。

相机采集采用 640×480、请求 30 FPS；这是采集请求，不是实测性能承诺。推理当前使用 VIDEO 模式串行处理，推理调用只阻塞识别进程；Unity 渲染独立运行。是否改为异步取最新帧，要依据相机联调时的实际延迟决定。

每条消息包含 `schema=1`、随机会话标记 `streamId`、递增 `sequence`、采集后的 Unix 毫秒时间 `capturedMs`、`tracked` 和 33 个 `{x,y,z,visibility}` 点。`x,y` 是原始未镜像画面的归一化坐标，模型输出的 `z` 不用于当前招式判定。

预览镜像与角色映射在显示层处理。消息不携带图像、音频或玩家身份，服务不保存姿态历史。服务只保留最新消息，慢连接超时退出；客户端单行限制 32 KiB，重连间隔约 1 秒，游戏在主线程读取最新消息。

接收方拒绝不支持的协议、错误点数、NaN/Infinity、不可靠的肩/肘/腕、出画的关键手臂点、超过 350 ms 的帧或明显来自未来的帧。时间戳是采集返回后的时刻，不代表传感器曝光时刻，因此仍须测量动作到电视反馈的整体延迟。

## 动作与状态

- 前 0.5 秒用于稳定输入；帧间中断超过 250 ms 时重新稳定。
- 手臂长度判定以肩宽归一化。相机严重侧拍、身体遮挡和儿童比例仍须实测调参。
- 挥拳需要先收手，再达到伸展条件；姿势保持不会连发。
- 防御姿势保持约 0.15 秒生效；光线姿势保持约 0.45 秒触发；双手举高约 0.6 秒触发变身。
- 变身、光线、防御形状优先于挥拳，以减少交叉姿势误触。
- 当前仅追踪一个主要人物，不提供可靠的身份锁定。原型试玩时先避免多人同时入镜。

`Battle` 状态机与 Unity 解耦，可以在 .NET 下测试。基本状态为等待、变身、战斗、暂停和胜利。怪兽依次休息、蓄力预警、攻击结算、恢复。摄像头断开时取消未命中的攻击，重新稳定 1.2 秒后恢复；家长手动暂停时必须先点击继续。

当前可调默认值：怪兽生命 24，普通攻击 1，能量上限 6，光线伤害 9。每次普通攻击或成功防御增加 1 能量。怪兽休息 4 秒，预警 2.4 秒，恢复 2 秒。未防御受击只触发恢复效果，不设玩家死亡；普通攻击也能结束战斗。

角色使用程序创建的原型几何体。上半身跟随相机二维手臂位置，招式时播放程序动作；尚未使用正式骨骼蒙皮模型。正式迪迦模型可替换 `PrototypeActor`，而输入与战斗规则保持独立。

## 测试边界

`tests/CoreChecks` 编译实际使用的 Core C# 文件，检查动作重置、持续姿势、左右拳、防御、光线、暂停恢复和胜利规则。通信集成检查启动真实 Python 服务，再由实际 C# TCP 客户端读取并校验。

自动检查不能替代 Unity 编译、画面验证、真实儿童动作测试和电视延迟测试。界面与呈现代码的验证进度见《验证记录》。
